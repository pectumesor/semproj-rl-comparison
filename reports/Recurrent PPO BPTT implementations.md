# Fix samples per update before comparing windows

A selectable BPTT window exists in RLlib (`max_seq_len`), Sample Factory (`recurrence`), rl_games (`seq_length`), TorchRL (`sub_traj_len`, `slice_len`), skrl (`sequence_length`) and MAPPO (`data_chunk_length`), but not in SB3-contrib, CleanRL, rsl_rl, PureJaxRL or Habitat. This repo's `RecurrentPPO` matches the field on state handling: it uses stored hidden states with no burn-in, and no PPO path in any library checked has a dedicated burn-in setting. It departs on one point that decides the comparison. **In every current library checked, the update count is independent of the window, while here it falls as 1/w**, giving 128, 32 and 8 updates at windows 16, 64 and 256 against 512 for the MLP. Stage 2's window ablation therefore varies BPTT length, update count, samples per update and total Adam path length together, and the logged diagnostics show the 8-update cell barely moving the policy. The repo should set envs per minibatch to **1024/w (64, 16, 4), which gives every window 128 updates of 1024 samples**. That is the geometry the LSTM's 3e-4 was tuned at, it reuses the 10 Stage 2 runs at window 16, and it needs 20 new runs. The tuned MLP stays as the reference, with a matched-geometry MLP as a sensitivity arm. `scripts/e4_lstm_updates.sh` should change before submission, because its 256/w arm is the most expensive option by far and would probably hit the 24 h limit at window 256. `scripts/e2_twin_rooms.sh` inherits the same confound in the paper's headline figure.

## Six libraries expose a window, and no current version lets it set the update count

The cleanest division among libraries is what a minibatch counts. RLlib, Sample Factory, rl_games and TorchRL fix timesteps per minibatch, so a longer window means fewer sequences per update. skrl, MAPPO, rsl_rl, PureJaxRL and Habitat fix the number of minibatches, which has the same effect. SB3-contrib fixes transitions through `batch_size`, and its maintainer's stated reason is that it avoids retuning the learning rate ([issue #103](https://github.com/Stable-Baselines-Team/stable-baselines3-contrib/issues/103)). CleanRL fixes `num_minibatches`. In the table, E is epochs, K is minibatches per epoch, D is rollout timesteps and S is minibatch size in timesteps.

Three qualifiers matter when citing this. SB3's window is not free: **`batch_size` below `n_steps` acts as an undocumented hard cap** that the source shows and the maintainer's answer omits ([issue #110](https://github.com/Stable-Baselines-Team/stable-baselines3-contrib/issues/110)). It couples window to minibatch, because `batch_size=64` gives a 64-step cap but only about 1.2 sequences per step in a simulated copy of the buffer, not the installed package. RLlib's behaviour is version-dependent: ray-2.9.0 sliced `minibatch_size` rows of sequences, the conversion to timesteps appears from 2.10.0, and it was still conditional in 2.40.0 ([ray-2.9.0](https://github.com/ray-project/ray/blob/ray-2.9.0/rllib/utils/minibatch_utils.py); [ray-2.40.0](https://github.com/ray-project/ray/blob/ray-2.40.0/rllib/utils/minibatch_utils.py#L132-L147)). That old behaviour is the only match found for this repo's semantics. Tianshou's `stack_num` is not truncated BPTT, as its PPO update passes no hidden state and its recurrent nets start from zeros ([ppo.py](https://github.com/thu-ml/tianshou/blob/f2402056b03acafeedf2518a5088db55add004ab/tianshou/algorithm/modelfree/ppo.py#L167-L200)). Acme's `unroll_length` belongs to a feed-forward PPO ([learning.py](https://github.com/google-deepmind/acme/blob/2e09e3ddecf4a1ba783688c92aa493c596a2beec/acme/agents/jax/ppo/learning.py#L338-L357)), and EnvPool has no learner at all. The notes read source code but ran no library, so the update counts are read from code, not measured.

## The repo matches the field on state and breaks from it on budget

Most of `RecurrentPPO` needs no defence. Starting each window from the hidden state stored at collection, with no burn-in, is what SB3, RLlib, Sample Factory, rl_games, skrl and MAPPO do ([buffers.py](https://github.com/Stable-Baselines-Team/stable-baselines3-contrib/blob/a8af63682070df0bda9707400b2e971055600910/sb3_contrib/common/recurrent/buffers.py#L216-L231); [add_states_from_episodes_to_batch.py](https://github.com/ray-project/ray/blob/891a5a8946fad05062daebc67bc04da3d78e78c0/python/ray/rllib/connectors/common/add_states_from_episodes_to_batch.py#L240-L297)). RLlib's `burn_in_len` is a DQN setting, and TorchRL's `BurnInTransform` is not wired into its PPO trainer ([dqn.py](https://github.com/ray-project/ray/blob/891a5a8946fad05062daebc67bc04da3d78e78c0/python/ray/rllib/algorithms/dqn/dqn.py#L174); [transforms config](https://github.com/pytorch/rl/blob/003c5f467f0f720e85aa8eb5884ce55e414c7f1d/torchrl/trainers/algorithms/configs/transforms.py#L688-L694)). The replay test, with log-probs and values matching collection to within 1e-6, covers the failure that this design most risks. Handling resets by zeroing state inside the window, without padding, matches CleanRL and MAPPO. Env shuffling is on the mainstream side, since rl_games, rsl_rl and skrl do not shuffle recurrent minibatches at all.

Two differences remain. The first is minor: windows are fixed and time-aligned (`algorithms/ppo.py` L683-L710), so every sample in a minibatch shares one time slice, and each env group walks its windows in temporal order. MAPPO instead permutes chunks across env and time ([shared_buffer.py](https://github.com/marlbenchmark/on-policy/blob/de66d7a4b23fac2513f56f96f73b3f5cb96695ac/onpolicy/utils/shared_buffer.py#L499-L512)), and SB3 moves its cuts every epoch. The second is decisive. Fixing the sequence count per minibatch is the off-policy convention: R2D2 uses 64 sequences of 80 steps with updates set by a replay ratio ([Kapturowski 2019](https://openreview.net/references/pdf?id=Hy7PKCFCQ)). On a fixed on-policy rollout, that convention forces updates to scale as 1/w.

The logged numbers show what this costs. Mean KL falls from 0.0036 at window 16 to 0.0008 at window 256, clip fraction falls from 3.6% to 0.5%, and explained variance sits at -1.85 at window 256, so the critic predicts worse than a constant. The 0.5% clip fraction is below the 1% line under which Hilton's advice says the iteration batch could be larger ([Hilton 2022](https://arxiv.org/abs/2110.00641)). These figures do not prove under-updating alone caused the weak critic, but they do mean **any Stage 2 result at window 256 is a joint test of long gradients and 8 updates**. One detail resists a simple reading: window 64 has a quarter of window 16's updates yet 81% of its KL. Lower gradient noise at 4096 samples could explain that, as could Luo's finding that RNN outputs shift more per parameter step as sequences lengthen, which comes from off-policy work ([Luo 2024](https://arxiv.org/html/2405.15384v1)). The data cannot separate them.

The closest published precedent for removing this confound is implicit. Pleines' sequence-length grid fixes the minibatch count in code, so the grid appears to have run at near-constant updates and about 2048 samples per update, though the paper does not call this a control and publishes no per-cell settings ([buffer.py](https://raw.githubusercontent.com/MarcoMeter/recurrent-ppo-truncated-bptt/main/buffer.py); [Pleines 2022](https://arxiv.org/abs/2205.11104)). It is also the only clean on-policy dose-response found. On Mortar Mayhem, success at 5 or more commands was 0.45, 0.67, 0.77 and 0.76 at lengths 16, 32, 64 and full episode, while Ballet barely moved with window at 2 dances. With 3 repeats per cell and no confidence intervals, that shape is a guide, not a prediction. Andrychowicz's warning that learning rate and minibatch size interact is the nearest explicit statement of the problem ([Andrychowicz 2021](https://arxiv.org/abs/2006.05990)). No study found varies updates per iteration by a factor of 64 in recurrent PPO.

## Holding 1024 samples per update gives the only cheap, tuned, reusable design

Each option below comes from updates = (256/minibatch) × (256/window) × 2, recomputed by script. Samples per update are envs × window. lr × U is learning rate times updates per iteration, a crude bound on Adam path length. `anneal_lr` is on, so realised values are lower, but ratios hold across all cells. The MLP stays at 512 updates of 256 shuffled transitions at lr 1e-4, or lr × U 0.0512. All figures use the repo's 64 envs and 2 epochs from `configs/algorithm/ppo.yaml`; the worked tables in the SB3 and library notes assume 32 or 16 envs and 10 or 1 epochs for illustration and do not describe this config.

| Option | Envs at w=16 / 64 / 256 | Updates per iteration | Samples per update | lr × U at 3e-4 | Sequences at w=256 | Stage 2 LSTM runs reusable | New runs |
|---|---|---|---|---|---|---|---|
| Fixed 64 (Stage 2 as run) | 64 / 64 / 64 | 128 / 32 / 8 | 1024 / 4096 / 16384 | 0.0384 / 0.0096 / 0.0024 | 64 | All 30, but confounded | 0 |
| 256/w (draft script) | 16 / 4 / 1 | 512 | 256 | 0.1536 | 1 | None; only the MLP's 10 runs match exactly | 30 |
| **1024/w (recommended)** | **64 / 16 / 4** | **128** | **1024** | **0.0384** | **4** | **Window 16 (10 runs)** | **20** |
| 4096/w | 256 / 64 / 16 | 32 | 4096 | 0.0096 | 16 | Window 64 (10 runs) | 20 |

Reuse covers the unmasked MLP-encoder LSTM at lr 3e-4, seeds 100-104 on medium_maze and hard_maze, 10 runs per window. The Stage 2 MLP reference at the same seeds and rooms remains valid under every option as a tuned-versus-tuned comparison. Any reused cell must have matching code, so the new cells should run from the same training code as Stage 2.

The 1024/w option wins on four grounds. It keeps every window at the geometry where 3e-4 was tuned, so window 16 is unchanged and needs no rerun. It keeps four sequences at window 256, matching Memory Gym's count at length 512 and exceeding CleanRL's two ([Pleines 2025](https://arxiv.org/abs/2309.17207); [CleanRL](https://github.com/vwxyzjn/cleanrl/blob/fe8d8a03c41a7ef5b523e2e354bd01c363e786bb/cleanrl/ppo_atari_lstm.py#L296-L306)). It places lr × U at 0.75 of the MLP's value, so the two backbones get similar path length without forcing either off its tuned setting. It also stays nearer the update counts where the on-policy stale-state evidence was gathered: Pleines found refreshing not worth its cost at about 24 to 32 updates per iteration, so 128 is about a 4x extrapolation of that null and 512 about 20x ([Pleines 2022](https://arxiv.org/abs/2205.11104)).

The 4096/w option is a sound sensitivity arm. It reuses window 64 and is the cheapest of the three to compute, but it moves window 16 to a quarter of its tuned updates, and it needs window 16's whole env set in each update. MAPPO's advice to avoid splitting data on hard problems favours it, while repo logs show that few updates at this learning rate leave PPO conservative ([Yu 2022](https://arxiv.org/abs/2103.01955)). Andrychowicz found larger batches did not hurt in the tested range, which only reached 256. Hilton's Procgen default uses this repo's exact 256 × 256 rollout with 8 minibatches per epoch, or 8192 samples per update, on a feed-forward CNN, so large batches are not unusual at this scale.

The 256/w option has the strongest headline, because it matches the MLP exactly in updates and samples. The case against it is not the one the notes make. One notes file calls a single sequence per minibatch unprecedented, but SB3 sits close to that: the simulated buffer at 256 × 256 with `batch_size` 256 gives 512 updates at 2 epochs with a mean of 1.98 sequences, and the zoo's `BipedalWalker-v3` config uses `n_steps` 256 with `batch_size` 256 ([ppo_lstm.yml](https://github.com/DLR-RM/rl-baselines3-zoo/blob/61956d90d9f8ac126043ed4024efa12a462d97e1/hyperparams/ppo_lstm.yml)). The real objections are learning rate, trust region and compute. At 3e-4 it runs at 3 times the MLP's lr × U. Under Hilton's square-root rule, today's cells translate to 1.5e-4, 7.5e-5 and 3.75e-5 at 256 samples, so 3e-4 is 2 to 8 times hotter ([Hilton 2022](https://arxiv.org/abs/2110.00641)). That rule assumes feed-forward networks, 1 epoch and an EWMA proximal policy, so treat it as an order of magnitude. Of the draft's two rates, 1e-4 is the defensible one. Per-minibatch advantage normalisation (`algorithms/ppo.py` L754) would also run on one env's rollout at window 256, and Hilton found normalisation scope matters at the smallest batch sizes.

Equal samples never mean equal information, and no option fixes that. A minibatch of 256 shuffled transitions is not one 256-step trajectory. Sequences per update fall from 64 to 4 across the recommended arm, and the effective sample size of a trajectory minibatch is unmeasured in any paper read. The paper should state this as a design choice, not claim neutrality.

The MLP needs one extra arm. Comparing tuned LSTM with tuned MLP answers "which backbone is better when each is set up well". It does not answer "which is better at the same budget". Ten runs of the MLP at 128 updates of 1024 samples, using `algorithm.mini_batch_size=1024`, cover that second question. Hilton's rule suggests about 2e-4 there. If the MLP's AUC moves materially, the LSTM-versus-MLP claim must carry that qualifier.

Learning rate should also get one short check, because a shared rate across windows is not automatically neutral. Engstrom's ablation grid-searches the rate per configuration ([Engstrom 2020](https://arxiv.org/abs/2005.12729)). The following sequence keeps that check on screening seeds, in line with the plan's rule that those seeds never support a claim.

| Step | Configs | Seeds and rooms | Runs |
|---|---|---|---|
| 1. Learning-rate pilot | 1024/w at w=16, 64, 256; lr 1e-4, 3e-4, 1e-3 | 0-2, medium_maze | 27 |
| 2. Confirmation | w=64 at 16 envs and w=256 at 4 envs, at the pilot's rates | 100-104, medium_maze and hard_maze | 20 |
| 3. MLP sensitivity | `mini_batch_size=1024`, lr about 2e-4 | 100-104, medium_maze and hard_maze | 10 |
| 4. Optional arms | 4096/w; 256/w at window 16 only, lr 1e-4 | 100-104 for 4096/w; 0-2 for the 512-update check | 20; 6 |

If the pilot moves window 16 away from 3e-4, its Stage 2 runs stop being reusable and step 2 grows to 30 runs. The Stage 2 cells at windows 64 and 256 should stay in the paper as a labelled fixed-sequence arm, since agreement across arms is a robustness result and disagreement is itself a finding about the confound. Hard_maze sat near the floor for the LSTM in the E0 probe, so medium_maze will carry most of the window signal.

## The draft script needs three changes before it costs a day

The first problem is compute, which the notes did not examine. `scripts/train.py` forces `device = "cpu"`, the launcher defaults to one CPU, and `SimpleLSTM.forward` calls `nn.LSTM` once per timestep. LSTM calls per iteration equal updates × window, or 131072/envs, so **cost follows envs per minibatch, not the window**. A local benchmark timed the repo's `SimpleLSTM` with small linear layers on one thread for one iteration of forward, backward and Adam, using random data and no resets. It excludes env stepping and the real encoder and ran on this Mac, not Euler, so only the ratios carry over.

| Window | Envs | Updates | LSTM calls per iteration | Seconds per iteration, per-step loop | Seconds per iteration, one call per window |
|---|---|---|---|---|---|
| 16 | 64 | 128 | 2,048 | 5.7 | 4.1 |
| 64 | 16 | 128 | 8,192 | 12.3 | 7.0 |
| 256 | 4 | 128 | 32,768 | 41.6 | 22.9 |
| 64 | 4 | 512 | 32,768 | 42.4 | 23.4 |
| 256 | 1 | 512 | 131,072 | 146.6 | 77.0 |

All three Stage 2 cells cost about the same in the benchmark (5 to 6 s). The draft's window 256 cell costs 26 times that, and the recommended one about 7 times. At the default 1000 iterations, the 24 h limit allows 86.4 s per iteration, and Euler's plain LSTM runs take 7-10 s per iteration in total. Assuming the update is about half of that, which is an estimate and not a measurement, the draft's cell lands near 95 to 135 s per iteration, so **it would be killed unless it stops early**, and the staged-ablation script records that a killed run saves no `auc.npy`. The recommended cell lands near 30 to 42 s, or 8 to 12 h. That fits the limit even with Euler's 2x spread between nodes, but it is the slow cell and needs a timing job first. A single `nn.LSTM` call per reset-free window, as SB3 does ([policies.py](https://github.com/Stable-Baselines-Team/stable-baselines3-contrib/blob/a8af63682070df0bda9707400b2e971055600910/sb3_contrib/common/recurrent/policies.py#L185-L206)), roughly halves it in the idealised no-reset case. That change would need the replay test rerun.

The second problem is the trust-region guard. `target_kl` is 0.04, so updates stop once running-mean KL passes 0.06. The highest current mean KL is 0.0036. If KL merely scaled with update count, window 256 at 512 updates and unchanged rate would reach about 0.05, and coherent drift would go well past that, so the guard could fire at window 256 alone. That scaling is a rough assumption, but the consequence is concrete: "512 updates" would become a nominal count that differs across windows. Only a `KL Break` flag is logged, so the realised update count should be logged too. Dossa's abstract reports that KL early stopping reduces sensitivity to update count ([Dossa 2021](https://doi.org/10.1109/ACCESS.2021.3106662)), which cuts both ways here, since it can also hide the variable being compared.

The third problem is tooling. `e4_promotion.py`'s `reference_fields` copies a level's fields and changes only `bptt`, so window 64 at `mb:16` looks for window 16 at `mb:16`, finds nothing, and loses its reference, because the reused window 16 run carries no `mb` field. The `mb` field needs handling there. Separately, `variant_name` records `algorithm.minibatch_size` for recurrent backbones only, so an MLP at `algorithm.mini_batch_size=1024` and lr 1e-4 would write into the reference MLP's folder. The two near-identical names are also a trap: `mini_batch_size` counts samples for the MLP and `minibatch_size` counts envs for recurrent agents. Windows 16, 64 and 256 cannot be swept as a Hydra cross product with minibatch sizes either, so each pair needs its own `run` line, as the draft already does.

The largest consequence sits outside E4. **`scripts/e2_twin_rooms.sh` sets no `minibatch_size`, so the LSTM windows run 128, 32 and 8 updates and the GRU at window 64 runs 32, against the MLP's 512.** Figure 3's lines use window 64, and hypothesis H2 says the LSTM fails once *L* passes the window. A failure at window 256 or a gap to the MLP in that figure would be confounded the same way. The timeline puts the full sweep at Nov 12-18, so it can still take the 1024/w pairs. This session did not check whether the *L* = 32 pilot has started, and it shares a timestamp with the sweep, so a change would need a fresh timestamp or a pilot rerun.

## Initialisation and history checks decide what a null result means

A flat window curve would be easy to over-read. The LSTM uses torch defaults: a repo-wide search of `models`, `utils` and `algorithms` found no orthogonal init, forget-gate bias or custom init anywhere, which also settles the gap the literature note left open. Jozefowicz found that small random init leaves forget gates near 0.5, and that a bias of 1 or 2 fixes the resulting vanishing ([Jozefowicz 2015](https://proceedings.mlr.press/v37/jozefowicz15.pdf)). A gate-only estimate gives a factor of 1.5e-5 across 16 steps at bias 0, 0.0067 at bias 1, and 0.13 at bias 2 (3e-4 over 64 steps). If that holds early in training, windows 64 and 256 add little reach at first, regardless of the task. Gates learn, so this is an early-training effect, and no PPO study tests it. CleanRL itself uses orthogonal weights with zero biases ([CleanRL](https://github.com/vwxyzjn/cleanrl/blob/fe8d8a03c41a7ef5b523e2e354bd01c363e786bb/cleanrl/ppo_atari_lstm.py)), so this is common practice, not a bug. Changing it would invalidate every existing LSTM run, so it belongs in a separate screening ablation, not the primary contrast: bias 1 at windows 16 and 256 on seeds 0-2.

Window coverage is smaller than the label suggests. With non-overlapping windows, a sample has on average 7.5, 31.5 and 127.5 earlier steps in its gradient path, so window 16 behaves closer to 8, in line with Elelimy's point that only the last sample gets a full T-step gradient ([Elelimy 2024](https://proceedings.neurips.cc/paper_files/paper/2024/file/1e616bde0438cb10cb6adf076ae7d336-Paper-Conference.pdf)). A cue 16 steps before its use shares a window with the decision 0%, 75% and 94% of the time, and a cue at 64 steps 0%, 0% and 75%. Nothing beyond 256 steps is directly trained at any setting, while E4 episodes run to 4096 steps. The forward state does carry older information, and short windows can still retain cues: Pleines' length-1 row reached 0.64 on Ballet at 8 dances ([Pleines 2022](https://arxiv.org/abs/2205.11104)), yet Rafiee found LSTM and GRU needed T at or above the interval to match RTRL in online prediction ([Rafiee 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC9814020/)). POPGym found memory-free policies did best on almost all navigation tasks ([Morad 2023](https://arxiv.org/abs/2303.01859)), so a flat result in E4's mazes may mean the task does not reward memory at that scale, which is why E2's controlled *L* matters more than E4's rooms.

Two diagnostics separate these readings cheaply, and neither needs a burn-in, which remains unjustified because no on-policy paper tests it. History-restricted evaluation, zeroing state k steps back on saved checkpoints, shows whether window 16 agents really use information older than 16 ([Kapturowski 2019](https://openreview.net/references/pdf?id=Hy7PKCFCQ)), and E2's junction reset is already a version of it. A staleness probe extends the existing replay test: after an update, compare outputs from stored and recomputed start states on the same batch. No published PPO counterpart exists, so report it as a diagnostic only. Log KL, clip fraction, gradient norm and advantage standard deviation per window alongside them. Finally, the paper should state window placement, forget bias, normalisation scope and reset handling explicitly. Time-aligned windows stay in the primary arm, because shuffling them across time would end the reuse of window 16.

## Conclusion

The question changed in the course of this review. It began as whether libraries offer a window, and most do, but the useful finding is that all of them treat the window as a free parameter by pinning the budget elsewhere. Here, the budget moves with the window, so Stage 2's three cells are three different training regimes, and the fix is one integer per window. The 1024/w design costs 20 runs and preserves the setting the learning rate was tuned for, while the intuitive "match the MLP exactly" design costs 30 runs, a retune and up to 26 times the update compute, and buys only a simpler sentence in the methods section.

The design itself has no published validation for 2D navigation, and nothing in the literature predicts this task's window curve. Its value is that the result becomes interpretable whichever way it falls: a gain with window would no longer be explainable by updates, and a flat curve could be tested against init and task horizon. The most urgent step is therefore not in E4. E2's sweep supplies the headline figure, and it is the one place where this fix is still free.
